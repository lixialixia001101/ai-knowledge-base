# 拉晶数据提取技能三处问题修复

> 分类：踩坑记录 | 日期：2026-11-24 | 状态：待补细节
> 关联项目：拉晶数据提取技能（Python）

## 背景

拉晶数据提取技能在整改中发现三处代码质量问题，需要逐一修复并沉淀修复方法论。

## 问题清单

| # | 问题 | 类型 | 严重度 | 状态 |
|---|------|------|--------|------|
| 1 | SQL 注入 | 安全 | 🔴 | 待补细节 |
| 2 | N+1 查询 | 性能 | 🟡 | 待补细节 |
| 3 | 硬编码密码 | 安全 | 🔴 | 已明确方案：.env + .gitignore + pre-commit 扫描 |

## 1. SQL 注入

- 位置：（待补充：文件/函数）
- 根因：字符串拼接 SQL，未使用参数化查询
- 修复方案：占位符 `%s`/`?` + 参数元组传参；动态条件改用白名单字段映射
- 通用经验：凡是"变量拼进 SQL 字符串"的写法一律视为缺陷，不管输入来源是否可信

## 2. N+1 查询

- 位置：（待补充）
- 根因：循环内逐条查库，批查改单查
- 修复方案：IN 批量查询 + 内存中按 key 分组组装；或 JOIN 一次取回
- 通用经验：看到"for 循环里出现 DB 查询"就先怀疑 N+1，先算数据量再决定批查还是 JOIN

## 3. 硬编码密码

- 根因：连接串/密码直接写在源码里
- 修复方案（已定）：
  1. 密码迁移到 `.env`，`.gitignore` 排除
  2. 仓库只放 `.env.example` 示例
  3. pre-commit 配 gitleaks 扫描，防止复发
- 通用经验：任何凭据进源码都是事故，历史提交里的密码即使删掉文件也留在 git 历史中，需要 filter-repo 清洗——所以最好的办法是从一开始就不进去

## 复盘

三处问题共同点：**都是"能跑就行"阶段留下的债**。修复顺序应按严重度：先 SQL 注入和硬编码密码（安全），再 N+1（性能）。
